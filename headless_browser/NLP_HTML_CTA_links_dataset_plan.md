# Подготовка данных для NLP-моделей: HTML, CTA и ссылки

Разбор пунктов 3 и 4 документа «ТЗ_DW_1_v5.pdf» от 21 октября 2026 года.

**Зона ответственности:** HTML-код, CTA и ссылки в электронных письмах.

**Задача:** подготовить данные для определения участия генеративного ИИ в создании и модификации этих элементов, включая частичное редактирование. Одной метки на всё письмо для этого недостаточно.

Ниже требования ТЗ отделены от предложений по реализации. Это схема данных и план экспериментов, а не готовый размеченный датасет.

## 1. Требования ТЗ к этой части

| Требование ТЗ | Практическое значение |
|---|---|
| 3.1, 3.3 — оценка письма и отдельных элементов | Нужны отдельные оценки HTML, CTA и ссылочных элементов |
| 4.1.2.1 — предобработка | Сохранять исходный HTML и извлекать текст, структуру и атрибуты |
| 4.1.2.3 — полная генерация и частичная правка | Подготовить примеры, где ИИ меняет всё письмо или только конкретный элемент |
| 4.1.2.4 — схема разметки | Хранить метку, способ генерации, генератор, язык, тип письма, зоны и символьные интервалы |
| 4.1.3.2 — калибровка | Подбирать пороги только на validation; test не использовать для настройки |
| 4.1.4.3 — границы зон | Возвращать вероятность и расположение элемента |
| 4.1.5 — объяснение | Показывать конкретные сигналы и фрагменты, повлиявшие на оценку |
| 4.5.1 — русский и английский | Нужны данные и проверка качества на обоих языках |

Обнаружение CTA и определение его происхождения — разные задачи. Сначала нужно найти призыв к действию, затем оценить участие ИИ в его создании.

Подозрительный URL, срочный призыв или шаблонная вёрстка сами по себе не означают AI-генерацию. Иначе модель будет определять фишинг или рассылки вместо происхождения элементов.

## 2. Какие данные собирать

| Объект | Что сохранять | Цель обучения |
|---|---|---|
| HTML | Исходный код, DOM-блоки, теги, атрибуты, CSS, комментарии и текстовые узлы | Участие ИИ в создании или изменении разметки |
| CTA | Текст призыва, ближайший контекст, положение и связанный HTML-элемент | Участие ИИ в написании CTA |
| Ссылка | `href`, текст ссылки, `title`, контекст и связанный CTA | Отдельно происхождение анкора и изменение URL или ссылочного элемента |

### HTML

Нужно различать следующие случаи:

- ИИ написал текст внутри готового человеческого шаблона.
- ИИ создал вёрстку вокруг человеческого текста.
- ИИ изменил только стили или один HTML-блок.
- ИИ создал и текст, и вёрстку.

Нельзя автоматически размечать весь HTML как AI-generated только потому, что внутри заменили текст кнопки. Метки содержания и структурной разметки должны различаться.

### CTA

CTA — не только кнопка. Фразы «Ответьте на это письмо», «Позвоните менеджеру», «Подтвердите участие» тоже являются призывами к действию.

На вход модели стоит давать сам CTA и соседний текст: у фразы «Подробнее» без контекста почти нет информации об авторстве.

### Ссылки

Модель могла написать «Посмотреть условия», но вставить предоставленный человеком URL. Тогда анкор создан ИИ, а адрес — нет.

Определять автора короткого URL по одной строке зачастую неинформативно. Полезнее анализировать ссылочный элемент вместе с контекстом и отдельно хранить историю изменения адреса.

## 3. Сценарии для датасета

Предлагаемая матрица сценариев — план подготовки данных, а не обязательные пропорции из ТЗ.

| Сценарий | HTML-разметка | CTA | URL |
|---|---|---|---|
| Полностью человеческое письмо | Человек | Человек | Предоставлен человеком |
| ИИ переписал CTA | Без изменений | ИИ | Без изменений |
| ИИ создал вёрстку | ИИ | Человек | Без изменений |
| ИИ изменил один HTML-блок | Частично ИИ | Может не меняться | Без изменений |
| ИИ переписал текст ссылки | Без изменений | По ситуации | Без изменений |
| ИИ изменил ссылочный элемент | По журналу изменений | По журналу изменений | Изменён ИИ |
| Полная генерация | ИИ | ИИ | Предоставлен или сгенерирован — отмечать отдельно |
| Человек отредактировал результат ИИ | AI-assisted | AI-assisted | По истории |

### Сложные отрицательные примеры

Обязательно включить:

- человеческие маркетинговые письма с профессиональной вёрсткой;
- шаблоны CRM и конструкторов рассылок без генеративного ИИ;
- короткие стандартные CTA: «Подробнее», «Купить», «Открыть»;
- человеческие письма с трекингом, UTM и длинными адресами;
- автоматические уведомления, созданные обычным шаблонизатором.

Автоматическая сборка письма программой не равна генерации нейросетью.

### Достоверность меток

Метки должны опираться на известную историю создания. Письмо из архива нельзя считать человеческим только потому, что оно реальное.

Неизвестное происхождение следует хранить как `unknown` и не использовать как достоверную обучающую метку. Это служебное состояние разметки, а не дополнительный итоговый класс: в ТЗ предусмотрен бинарный вердикт.

## 4. Схема разметки

Удобно хранить исходное письмо и связанные записи зон.

| Поле | Назначение |
|---|---|
| `email_id`, `parent_email_id` | Письмо и исходник, из которого сделана вариация |
| `group_id` | Группа связанных писем для разбиения без утечек |
| `language`, `email_type` | Язык и тип письма |
| `generation_method` | Человеческое, полная генерация, частичная правка, правка человеком после ИИ |
| `generator_model`, `generator_revision` | Точный генератор и версия |
| `prompt_id`, `generation_params` | Воспроизводимость генерации |
| `zone_id`, `zone_type` | Конкретная зона: HTML, CTA или ссылка |
| `source_field`, `start`, `end` | В какой строке и где находится зона |
| `label_ai` | Бинарная метка зоны; `null` при неизвестном происхождении |
| `ai_spans` | Сгенерированные интервалы внутри зоны |
| `annotation_source` | Журнал генерации, подтверждённая история или ручная проверка |

### Пример записи

Ниже иллюстративная запись CTA, а не готовый обучающий пример.

```json
{
  "email_id": "mail_001_variant_02",
  "parent_email_id": "mail_001",
  "group_id": "family_001",
  "language": "ru",
  "email_type": "marketing",
  "generation_method": "partial_rewrite",
  "generator_model": "<точный ID генератора>",
  "zone_id": "cta_01",
  "zone_type": "cta",
  "source_field": "zone_text",
  "zone_text": "Узнать больше",
  "start": 0,
  "end": 13,
  "label_ai": 1,
  "ai_spans": [
    {"start": 0, "end": 13}
  ],
  "annotation_source": "controlled_generation"
}
```

Для реальной записи дополнительно нужны координаты элемента в письме и окружающий контекст.

### Символьные интервалы

Границы следует фиксировать как `[start, end)` в Unicode-символах конкретного поля: начало включается, конец не включается.

Координаты в исходном HTML и в очищенном тексте различаются. Их нужно сохранять отдельно и поддерживать соответствие. После очистки HTML старые индексы использовать нельзя.

Сгенерированные интервалы лучше получать из контролируемой операции замены:

1. Выбрать блок исходного письма.
2. Передать его генератору с заданием на изменение.
3. Получить новый блок.
4. Вставить его программно.
5. Вычислить границы вставленного фрагмента кодом.

Просить LLM самостоятельно посчитать символьные индексы ненадёжно.

## 5. Подготовка и разбиение выборок

1. Собрать письма с подтверждённым происхождением, отдельно выделив корпоративные письма и маркетинг.
2. Дедуплицировать и объединить близкие письма, кампании и шаблоны в группы.
3. Разделить группы на train / validation / test, например 70 / 15 / 15.
4. Генерировать вариации внутри соответствующего разбиения.
5. Проверить, что изменены только запрошенные зоны, а границы корректны.
6. Отдельно проверить переносимость на генератор, которого не было в обучении.

Исходное письмо и все его вариации должны попадать в один split. Иначе тест будет измерять запоминание шаблонов.

Для пилота можно ориентироваться на 1–2 тысячи независимых исходников и несколько контролируемых вариаций каждого. Это проектная оценка, не гарантия качества.

Упомянутые в ТЗ 1941 письмо — требование к обработке каталога, а не подтверждение наличия готовой обучающей разметки.

### Защита от артефактов генерации

- Не создавать весь положительный класс одним генератором и одним промптом.
- Не допускать, чтобы только AI-примеры содержали `example.com`, одинаковое форматирование или служебные фразы.
- Сохранять сопоставимое распределение языков и типов писем между классами.
- Хранить модель, параметры, версию промпта и историю преобразований.
- Выполнять генерацию на реальных письмах в разрешённом контуре: ТЗ запрещает передачу их содержимого внешним сервисам без согласования.

## 6. Модели до 1B параметров

Все перечисленные модели — заготовки для обучения, не готовые детекторы AI-писем. Назначение в последнем столбце — рекомендация для экспериментов.

Число параметров приведено приблизительно; конкретная задача и классификационная голова могут немного менять размер.

| Модель | Параметры | Языки | Применение |
|---|---:|---|---|
| [RuBERT-tiny2](https://huggingface.co/cointegrated/rubert-tiny2) | 29,4M | RU | Быстрый старт для CTA и анкоров; замороженные эмбеддинги или дообучение |
| [DistilBERT multilingual](https://huggingface.co/distilbert/distilbert-base-multilingual-cased) | 134M | RU + EN | Компактная единая модель для двух языков |
| [ruBERT-base](https://huggingface.co/ai-forever/ruBert-base) | 178M | RU | Сравнение с tiny на русскоязычных зонах |
| [XLM-RoBERTa-base](https://huggingface.co/FacebookAI/xlm-roberta-base) | 278M | RU + EN | Основной кандидат для двуязычной классификации и локализации |
| [ruRoBERTa-large](https://huggingface.co/ai-forever/ruRoberta-large) | 355M | RU | Более тяжёлый эксперимент для русского |
| [ruBERT-large](https://huggingface.co/ai-forever/ruBert-large) | 427M | RU | Дополнительное сравнение при достаточном объёме данных |

RuBERT-tiny2 ориентирован на русский язык. DistilBERT multilingual обучен на 104 языках. XLM-R предназначен в том числе для дообучения на классификацию последовательностей и токенов.

Для HTML можно дополнительно экспериментировать с [CodeBERT-base](https://huggingface.co/microsoft/codebert-base), но обучение на коде CodeSearchNet не доказывает пригодность для определения происхождения HTML-писем. Проверять его стоит после простого структурного baseline.

### Рекомендуемая первая реализация

| Компонент | Подход |
|---|---|
| HTML | Структурные признаки + символьный TF-IDF + логистическая регрессия |
| CTA и текст ссылок, русский пилот | RuBERT-tiny2 |
| CTA и текст ссылок, RU + EN | Multilingual DistilBERT |
| Следующий эксперимент | XLM-R-base |
| Локализация | Классификация токенов с переводом результатов в символьные интервалы |
| Объединение | Калиброванный классификатор над оценками зон и структурными признаками |

Замороженные эмбеддинги + обучаемый линейный классификатор и полное дообучение энкодера — разные режимы. Их следует оценивать отдельно по качеству и времени.

## 7. Ограничения ТЗ

### Время обучения

В таблице 2 указано до 10 минут на CPU на обучение всех моделей и калибровку. Полное дообучение BERT нельзя заранее считать соответствующим этому условию.

Для строгого выполнения разумнее начать с признаков или замороженных эмбеддингов и линейных классификаторов. Время извлечения эмбеддингов также нужно замерять отдельно и явно описывать.

### Сохранение моделей

В п. 4.1.3.3 буквально сказано сохранять модели и параметры обучения в JSON. Для нейросетей обычный вариант — веса в `safetensors`, конфигурация и калибровка в JSON. Такое отступление нужно согласовать.

### Общесистемный метод оценки

Пункт 4.1.3.4 требует как минимум метод с языковой моделью или комбинированный метод. Соответствие локально дообученного энкодера всем требованиям к общесистемному режиму оценки, включая API и архитектуру, нужно отдельно зафиксировать в проектном решении. Один классификатор твоих зон не закрывает автоматически весь объём системы.

## 8. Метрики

| Метрика ТЗ | Требование |
|---|---:|
| ROC-AUC | ≥ 0,70 |
| F1 на калиброванном пороге | ≥ 0,70 |
| FPR на человеческих письмах | ≤ 0,20 |
| FPR на легитимном маркетинге | ≤ 0,20 |
| ROC-AUC: частичная генерация против человеческих писем | ≥ 0,70 |
| Локализация, F1 по символам | ≥ 0,60 |

Это общесистемные показатели ТЗ. Для этой зоны ответственности дополнительно следует считать качество отдельно по HTML, CTA, ссылкам и языкам.

Пороги и калибровка подбираются только на validation. Test используется для финальной оценки.

## 9. Что необходимо для реального датасета

- Архив исходных EML.
- Сведения о происхождении писем и допустимости использования.
- Согласованный перечень типов зон и правила их разметки.
- Доступ к локальным моделям-генераторам.
- Журнал контролируемых преобразований.
- Проверка корректности извлечения элементов и символьных границ.
- Фиксированные разбиения без утечек.
